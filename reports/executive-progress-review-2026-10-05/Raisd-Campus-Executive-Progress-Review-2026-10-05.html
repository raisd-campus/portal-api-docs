1. Executive snapshot

Raisd is building four modern portals (Applicant, Student, Lecturer, Staff) on the existing campus CMS through a single Portal API. The Working Group selected Lesotho as the first acceptance campus (M4) on 3 Oct 2026. Product sequence remains admissions-first: confirm rules (M1) → admissions Live (M2) → core student journeys (M3) → Lesotho acceptance (M4) → other campuses (M5).

3.2 Near-term intentions (next engineering focus)

Protect admissions-first priority

  • Freeze non-critical student Demo polish unless it is on the M2 path (auth, accessibility, mobile shell).
  • Prioritise CAP-53, applicant CAP-02/03/07/55, and Registry old-CMS verification.
  • Keep student demos labelled Demo until wired to durable SoR.

Close leadership blockers (M1)

  • Named owners for rules, API access, and operating checks.
  • Agree kickoff and first target weeks (currently TBC).
  • Confirm backend commitment path for CMS bridge.

Lesotho pilot readiness (M4 path)

  • Secure agreed Live SoR path / old CMS dump (no PII in repos).
  • Map NMDS, LGCSE, Loti, and newer-CMS parity gaps.
  • Treat CAP-41 training/ops as part of acceptance, not an afterthought.

Projected outcome for leadership

  • This phase (M1–M4): modern portals on existing CMS; Lesotho accepts first.
  • Success metric: Live checklist moves off 0% on admissions, then core journeys.
  • Not the goal yet: rewriting every staff desk or pulling M5 ahead of M2 Live.

3.4 Definition of done (any capability)

  1. Real data from the system of record (not a mock session).
  2. Durable save where the user can mutate data.
  3. Server-enforced permission for that role and campus.
  4. Paired staff/lecturer action exists in new UI or is verified in the old CMS.
  5. Accountable owner named.
  6. Core mobile accepted if the capability is in the mobile product set.
  7. Country/campus operating checks closed or explicitly waived.
