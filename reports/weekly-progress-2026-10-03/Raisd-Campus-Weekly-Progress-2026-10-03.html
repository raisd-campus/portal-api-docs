1. Executive summary

2.2 Decisions needed this meeting (detail)

These five decisions are the working-group agenda items that unblock Live work on Admissions (M2). Each decision states why it matters now, the options, the recommended default for discussion, and what happens if we leave it open. Record the outcome in the checklist Timeline tab and SDD-10 decision log in the same meeting if possible.

D1 — Delivery sequence: keep admissions-first?

Why now. Product priority (7 Sep) is Cyberjaya first and Admissions before semester registration. Engineering reality has been the opposite for weeks: Student Demo is deepest (M3 depth). Applicant Demo UI has now started and is deployed — so the sequence question is no longer theoretical. We must either reconfirm M2 as P0 or explicitly change product priority.

OptionMeaningConsequence
(a) Reconfirm admissions-first Recommended Applicant journeys + CAP-53 admissions slice are P0. Student Demo continues only for shared design-system reuse, gate hygiene, and blockers that Applicant also needs. Build aligns with M2 Live path; student polish is deprioritised.
(b) Promote student Demo as near-term showpiece Accept that stakeholder walkthroughs centre on enrolled-student UX; Admissions Live slips until CAP-53/Applicant catch up. Must update the sheet / SDD sequence so the group is not measuring against admissions-first while funding M3 depth.
If we do nothing: effort drifts back to more student Demo while Applicant / Registry Live remains empty. Weekly status will keep looking “busy” without moving Live count off 0 on the critical path.

D2 — CAP-53 / old CMS API ownership and access

Why now. CAP-53 (Portal API ↔ existing Cyberjaya CMS) is the only shared item marked Partial and gates every Live student/applicant write. We have dump inventories and api_student_* / desk evidence, but no named owner, no granted callable HTTP surface, and Portal API still runs cms.mode = stub with Neon Demo persistence. Without D2, Demo forever.

OptionMeaningConsequence
(a) Name owner + grant access this week Recommended Assign a backend / old-CMS owner. Grant read (then controlled write) access for an admissions slice: apply → evidence → offer → enrol mapping to existing SPs/tables. Engineering can start a real CAP-53 spike with evidence, not guesses.
(b) Time-box a paired spike Frontend + CMS pair for 3–5 days to document callable methods, auth, and first write path; owner named by end of spike. Faster discovery if a single owner is not ready, but still needs access credentials.

Related open questions: Q1 (stack/access), Q2 (CMS owner / callable surface), Q26 (map api_student_* / portal_r_student_* to Portal API methods).

If we do nothing: Neon Demo keeps looking “persistent” while Live count stays 0. Applicant UI cannot graduate beyond Demo.

D3 — Cyberjaya Live login path (CAP-01)

Why now. Student Demo already has student-number + password login (gitignored credentials; Portal API validates). That is not campus identity. Applicants and enrolled students need an agreed Live path before CAP-01 can leave Demo/Placeholder. Choice also drives Portal API session design, password reset ownership, and whether applicants share the same IdP as students/staff.

OptionMeaningBest fit
(a) CMS credentials via Portal API Portal API authenticates against existing CMS user store / login rules; issues portal session only after CMS accepts. Fastest path if CMS login is already the campus source of truth.
(b) Campus SSO with CMS mapping External IdP (SSO); Portal API maps identity to CMS person/student/staff records before authorising. Better long-term UX; needs IdP owner + attribute mapping + fallback for applicants who are not yet “users”.
(c) Both, with a clear primary Likely e.g. applicants use CMS/account-create path; enrolled students/staff use SSO (or the reverse). Document primary per audience. Matches mixed campus reality; must avoid two conflicting passwords without a policy.
If we do nothing: CAP-01 cannot go Live; every journey that assumes real sign-in stays Demo theatre.

D4 — Named department owners and kickoff week

Why now. All checklist next-action owners and target weeks remain TBC. Schema v3 also needs per-campus policy confirmation (CS-01–CS-11) from Registry / Bursary / IT before Live features. Without names and a kickoff week, weekly meetings have no calendar and “Needs checking” never closes.

If we do nothing: SDD-13 stays “all TBC”; Demo work has no accountable path to Live; weekly packs cannot report closed decisions.

D5 — Durable file store for Live evidence

Why now. Admissions evidence (CAP-03), profile documents (CAP-09), assignment files (CAP-20), and payment proofs (CAP-46) all require a store staff workflows can open. Current portals keep session/metadata Demo uploads only. Choosing the store early avoids rebuilding Applicant upload UX twice.

OptionMeaningTrade-off
(a) Reuse existing CMS document trees / stdfile paths Recommended default Portal API writes files through the same channels staff already use in the old CMS. Least migration risk; constrained by legacy layout and access rules; needs owner confirm of live paths (Q25).
(b) Object store + CMS metadata linkage New blob store for bytes; CMS (or Portal API) holds metadata and ACL. Cleaner modern path; more infra + dual-read during transition; still needs CMS visibility for staff desks.
(c) Defer Live files; Demo metadata until M3 Keep Applicant/Student uploads as Demo-only until after core journeys exist. Unblocks screens faster but blocks M2 Live for any journey that legally needs evidence on file.
If we do nothing: CAP-03 / 09 / 20 / 46 cannot go Live; Admissions launch cannot meet “real records” release conditions.
Meeting ask: Vote or assign D1–D5 before deep feature demos. Minimum useful outcome today: D1 choice recorded, D2 owner named (or spike dated), D4 kickoff week + at least Registry and IT owners named.
