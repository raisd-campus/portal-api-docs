This phase vs longer term (23 Sep 2026 — Aslam). Cyberjaya CMS remains SoR; portals via Portal API; no duplication of operational functions. Longer term: progressive unified one-stop CMS on verified gaps + migration strategy (M5+). See LUCT CMS — target delivery and architecture overview.
Student ↔ programme mapping. Students map to a programme version: StudentProfile → ProgrammeEnrolment → programmeVersionId → ProgrammeVersion → Programme. Keep version pinning (e.g. BBA 129 vs 122 credits). See ERD.
Campus where a programme is offered. Prefer ProgrammeCampusOffering (version × campus), not Faculty-as-campus. Faculty remains organisational. See ERD curriculum and architecture.
LUCT compatibility. Do not mirror legacy CMS tables. Document CAP-53 as an anti-corruption layer, legacy ID maps, idempotent writes, reproducible calculations, layered “active” statuses, and one SoR owner per domain. Start here: Architecture — LUCT CMS / Portal.

How to read these diagrams

CMS (SoR) Existing campus CMS remains system of record; CAP-53 translates.
Canonical model StudentProfile → Enrolment → StudyPeriod → ModuleRegistration → ModuleResult.
Postgres (planned) Portal-owned maps, DQ, audit, session — not a second SoR for CMS domains.
Evidence volume File bytes for assignments, payment proofs, admissions evidence.

Cardinality notation in ERDs follows Mermaid: ||--o{ one-to-many, ||--|| one-to-one, }o--o{ many-to-many via junction. DFDs use Gane & Sarson style via Mermaid flowcharts.
