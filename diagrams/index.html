Executive summary

Raisd is modernising how applicants, students, lecturers, and staff use campus systems — without throwing away the working campus CMS family that already holds the official records. Lesotho is the pilot project and first acceptance campus (Working Group, 3 Oct 2026 — supersedes Cyberjaya-first).

Think of it as four new front doors (Applicant, Student, Lecturer, Staff) that all talk to one Portal API. That API is the only bridge to the existing CMS. Nobody’s browser talks to the database or file store directly.

This phase (confirmed 23 Sep 2026; pilot campus updated 3 Oct): keep the existing campus CMS family as the system of record; ship better portal experiences; do not rebuild operational desks that already work; aim for parity with Lesotho’s newer CMS. Longer term: one unified Raisd CMS with databases placed by country (Lesotho, Malaysia, Singapore, Sierra Leone, Botswana, …), white-labelling, and feature toggles — reached via M5 progressive migration, not a launch rewrite.

  1. Now: student UI is largely demo/mock; applicant / lecturer / staff portals and live CMS writes are still ahead.
  2. Next: agree rules (M1), then admissions end-to-end on real records (M2).
  3. Then: core student journeys (M3), Lesotho pilot acceptance (M4), other campuses including Cyberjaya (M5), then distributed ideal.

Four role portals → Portal API → anti-corruption layer (CAP-53) → existing CMS. Planned Postgres holds portal maps, audit, and session — not a second copy of CMS data. Detail: Architecture review · SDD-02 · ADR-1.

Current state, target state, and what needs to be done

Baseline product truth: SDD-01. “Demo” on screen is not “Live” — Live needs durable save, real records, and server-enforced permissions.

Current state

  • Student portal: deepest UI, still mostly demo / mock data.
  • Applicant, lecturer, and staff portals: not launched as Live products.
  • Backend: contracts and mock runtime; CMS writes not Live.
  • Auth: mock student session; real SSO / CMS login still ahead.
  • Staff work: continues on the existing LUCT CMS desks.
  • Docs & diagrams: published for the working group (this site).

This-phase target (M1–M4)

  • Four portals on real campus CMS records via Portal API — Lesotho pilot first.
  • Admissions first, then core student journeys and Lesotho acceptance (M4).
  • Parity with Lesotho’s newer CMS (screenshots); staff stay on verified old CMS unless a gap is proven.
  • Phone-friendly core journeys (not a native app mandate).
  • Monitoring, backups, privacy, and training ready for Lesotho pilot go-live.

What needs to be done

  • Agree campus rules, owners, and API access (M1).
  • Ship Portal API first slice + admissions end-to-end (M2 / CAP-53).
  • Wire Live auth that respects CMS login rules.
  • Make student learning, fees, and support paths Live or keep them on verified old CMS (M3).
  • Complete Lesotho pilot acceptance and ops readiness (M4).
  • Only then expand campuses and migrate remaining CMS domains with a written strategy (M5).
Longer-term direction (M5+ → ideal): a progressive unified one-stop CMS — retire legacy desks domain-by-domain when ownership, cutover, rollback, and training are agreed. Ideal end state: one product with distributed country databases, white-label, and feature flags ((one-page architecture)). Not a rewrite mandate for Admissions launch. See target delivery.
