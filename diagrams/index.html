Campus portal data model & flows

Detailed Mermaid entity-relationship and data-flow diagrams for the Raisd control plane: Portal API, role portals, existing CMS (system of record), planned Postgres, and evidence file storage. Derived from Zod portal contracts and the Software Design Documents.

Logical model (contracts + SDD) Students map via programme version Campus via Faculty → Programme No physical SQL migrations yet Public: raisd-campus.github.io/portal-api-docs/diagrams
Student ↔ programme mapping. Students are mapped to a programme version, not only to a programme: StudentProfile → ProgrammeEnrolment → programmeVersionId → ProgrammeVersion → Programme. Details on the ERD (domain map and student record sections).
Campus where a programme is offered. Via faculty: Campus → Faculty → Programme → ProgrammeVersion. Enrolment also stores campusId for the student’s study campus. See the ERD institution and curriculum sections.

How to read these diagrams

CMS (SoR) Existing campus CMS remains system of record until CAP-53 adapters land.
Portal contracts Canonical record shapes in sibling student-portal Zod schemas.
Postgres (planned) Portal-owned durable state designed in SDD-12; not migrated yet.
Evidence volume File bytes for assignments, payment proofs, admissions evidence.

Cardinality notation in ERDs follows Mermaid: ||--o{ one-to-many, ||--|| one-to-one, }o--o{ many-to-many via junction. DFDs use Gane & Sarson style via Mermaid flowcharts (external entities, processes, data stores).
