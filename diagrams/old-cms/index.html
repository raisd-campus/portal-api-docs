Existing Cyberjaya CMS — technical analysis

Inventory and CAP mapping from the Cyberjaya source & structure package (CMS_Cyberjaya_Source_Codes_&_DB_Structure_23_09_2026). Per ADR-1, the old CMS remains the system of record; Raisd portals and the Portal API sit in front and must acknowledge CMS writes for Live.

This phase — ADR-1 (confirmed Aslam, 23 Sep 2026). Use the existing Cyberjaya CMS as system of record. Build modern portal experiences via the Portal API → CAP-53 anti-corruption layer → existing MySQL. Do not duplicate operational staff functions the old CMS already runs. Also seen in dumps: campus2_cyberjaya, portalcyberjaya.
Longer-term target. Still aim for a unified, one-stop CMS, delivered progressively on verified gaps with an explicit migration strategy (ownership, cutover, rollback, training). That consolidation sits under M5+ / remaining-CMS work — not Admissions launch rewrite. See SDD-03 and high-level comparison & target delivery. CAP / milestone IDs: SDD-15 nomenclature, SDD-11 catalogue.
Technology shape. PHPMaker core under cyberjaya/campus/<desk>/, plus Laravel sub-apps payment/ and icupdpa/. Live classes use Adobe Connect tables and classroom.limkokwing.net streaming. Batch ops live in cyberbatch/ and CYBERJAYA-SCRIPT/.

Context — old multi-app CMS vs Raisd portals

Staff currently log into many PHPMaker (+ Laravel) desk apps that share MySQL. Raisd collapses student/applicant/lecturer/staff UX into four webs that talk only to the Portal API.

Side-by-side context
