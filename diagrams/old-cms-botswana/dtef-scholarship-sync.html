Botswana — DTEF scholarship sync with TEF.gov.bw

Functional process and technical analysis of the Registry desks that push student admission / programme-of-study records to Botswana’s national tertiary financing portal (TEF at tef.gov.bw). Evidence from package CMS_Botswana_Source_Codes_&_DB_Structure_24_09_2026 — especially r_scholarshipapplist.php and r_dropout_scholarshipapplist.php (sync runs on the matching edit screens).

Gov API · Drupal HAL+JSON Table r_scholarshipapp CAP-48 adjacent M5 campus-local · not ADR-1 SoR
Scope. Structure and behaviour only. PHP sources, TEF Basic Auth credentials, and live student payloads are not committed. Canonical agent notes: botswana-dtef-scholarship-sync.md. Parent inventory: Botswana CMS analysis.

1. Functional specification

Registry prepares DTEF-bound admission rows; saving with status 31 (Sent by Registry) submits to TEF. Finance assist billing is a separate CMS process.

End-to-end process

CMS queue → TEF admission API → later DTEF outcome statuses.

  end

2. Technical analysis

Sync is implemented in the edit screens’ EditData(), not in the list PHP. Lists own filters, status labels, and (dropout) CSV upload UI.

TEF API contract

StepRequestNotes
1 · CSRF GET https://tef.gov.bw/rest/session/token Token value sent as X-CSRF-Token
2 · Admission POST https://tef.gov.bw/api/post/studentadmissions?_format=hal_json Content-Type: application/hal+json · HTTP Basic (credentials in PHP — not published here)
Entity type[].target_id = program_of_study Drupal HAL entity shape (field → [{ value: … }])
Duplicate Error text Duplicate Student Admission! Treated as non-fatal → status 32

Primary table r_scholarshipapp

PK schctr; person + programme + cost fields; workflow app_status, date_sent, staffid, remark. Active list reads view r_scholarshipapp_v (join to r_student for contact).
