Cambodia certificate QR + Verification

How LUCT Cambodia CMS Registry generates certificate QR codes via the external Limkokwing QR SaaS, and how public scans land on the Verification site. Evidence from Vara’s CMS pack (7 Oct 2026) and QR / Verification Drive packs (8 Oct 2026). M5 campus integration — not Lesotho M4 Applicant Demo letters.

1. Summary

Certificate QR is not generated inside Portal API or the Applicant Demo. Cambodia Registry PHP calls an external QR registry; the QR payload is a URL into the public Verification app. Vara (8 Oct): “Do check in CMS Cambodia, there's a call to the QR system to generate the QR code.”

Three systems

SystemRoleHost / path
Cambodia CMS (Registry) Builds short_code + verify URL; POSTs create API; saves PNG cambodia/registry/qrcode_gen*.php (campus SoR)
QR System (SaaS) Registers QR identity; returns base64 PNG https://qr.limkokwing.net/api/create_qrcode_api
Verification site Public scan target; shows cert validity for campus path https://verification.limkokwing.net/cambodia/{token}

2. Runtime flow

Observed from current-style qrcode_gen.php (Mar 2026). Inputs arrive as query params: StdProgramID, StudentID, ProgramCode.

Issue (Registry) then scan (public)

Create stores the Verification URL in the QR DB, but the PNG itself encodes the short SaaS URL. Scans hit QR → HTTP redirect → Verification.

Issue checklist (Registry)

  1. Build short_code = KHM-PNH_{StdProgramID}.
  2. Encrypt StdProgramID → base64 token; build Verification URL under /cambodia/.
  3. POST create API (see §3). SaaS stores url; PNG encodes short redirect URL.
  4. Parse JSON field Qrcode (base64 PNG); save as {StudentID}_{ProgramCode}.png.

Response (from QR System ApiController)

  • JSON; field Qrcode = base64 PNG. Also status (1 success / 0 error-or-exists) and message.
  • If short_code already exists: returns existing PNG with status: 0, message “QR code already exists” (CMS still gets an image).
  • PNG payload data = {base_url}/qrcode/{short_code}, not the Verification URL. Redirect resolves the stored url.
  • Image via Endroid QR Code (300px, medium ECC). Stored under writable/uploads/qrcodes/{short_code}.png.
  • Category auto-created by name if missing (description “Auto-created category”) — how LUCT appeared in the dump.

5. Verification pack (inventoried)

Zip verification.limkokwing.net_source_code_08_10_2026.zip is small (~13 KiB): a front controller, crypto helper, Cambodia cert model, Apache rewrite, and docker stubs. No full framework tree.

Request path

flowchart TD
  A["GET /{country}/{token}"] --> B[urldecode token]
  B --> C[AES-256-CBC decrypt]
  C --> D[StdProgramID]
  D --> E["CALL GetStudentCertInfo(StdProgramID)"]
  E --> F{Row found?}
  F -->|yes| G[Certificate Verified UI]
  F -->|no| H[No certificate found]
  • Apache .htaccess rewrites all non-files to index.php.
  • First path segment is treated as country (UI hard-codes campus label “Cambodia” today).
  • Decrypt supports plain numeric StdProgramID or legacy …_timestamp_date forms (takes trailing segment after last _ when non-numeric).

CMS stored procedure GetStudentCertInfo

Defined on campus2_cambodia (CMS procedures dump 7 Oct 2026). Verification calls it over MySQL with a dedicated DB user (credentials in pack — ops secret, not published).

  • Input: StdProgID (varchar).
  • Reads r_studentcert_cambodia + join s_upload where UploadType in (11) for cert image blob.
  • Returns: StdProgramID, StudentID, StudentName, PicURL, ProgramCode, ProgramName, GraduationDate, CertSN, CertFileBlob, CertFileName, CertFileType.

Verified page fields

  • Student photo (PicURL), name, Student ID
  • Programme name · Campus label “Cambodia” · Graduation date
  • Certificate serial (CertSN) · inline certificate PNG from blob when SN present
  • Footer branding: “Raisd AI”
Ops risk — AES key sync. Pack copies of CMS qrcode_gen.php and Verification lib/Encryption.php use different AES key/IV material (fingerprints differ). Live systems must keep encrypt/decrypt keys aligned; Raisd adapters should take secrets from vault, not from checked-in dumps.

6. Verify token & short code

Public Verification URL

https://verification.limkokwing.net/cambodia/{token}

  • {token} = base64(AES-256-CBC ciphertext of StdProgramID).
  • URL-encoded when appended (urlencode / rawurlencode depending on script).
  • Stored as qrcode.url in the SaaS. The PNG encodes qr.limkokwing.net/qrcode/{short_code}, which 302-redirects here.
  • Key material in Registry + Verification PHP — ops secret; never republish. Packs currently disagree (see §5).

Short-code convention

PartValueMeaning
CountryKHMCambodia (ISO-ish campus code)
City / campusPNHPhnom Penh
Separator_
SerialStdProgramIDStudent–programme row id from CMS

Raisd should treat short-code allocation as owned by the QR SaaS + campus convention — do not invent a parallel allocator in Schema without campus agreement.

Crypto evolution (high level)

  • Current path: OpenSSL AES-256-CBC of StdProgramID alone (commented older path appended _timestamp_YYYYMMDD).
  • Legacy: qrcode_gen1.php / early helpers used mcrypt Rijndael — obsolete; not the create-API path.
  • Local-only QR: early qrcode.php built images with phpqrcode against Verification base URL — superseded by SaaS create API.

9. Raisd implications

  1. Campus integration, not Portal API core (Lesotho M4). Applicant Demo DEMO PDFs must not pretend to be this certificate QR path.
  2. Three hops on scan: PNG → QR short URL → Verification → live campus2_cambodia via GetStudentCertInfo. Raisd Live must not break the SP or upload-type 11 cert blob join.
  3. QR SaaS is shared infrastructure (namecards + marketing + certs). This dump’s certificate short-codes are Cambodia-only (KHM-PNH_); other campuses may adopt new prefixes later.
  4. M5 adapter: after official cert issuance, POST create API (TLS verify on, secrets in vault). Expect idempotent “already exists” responses. Prefer documenting Cloudflare allow-lists over disabling SSL verification.
  5. AES keys must match between encrypt (Registry/adapter) and decrypt (Verification). Do not ship pack keys into git; resolve live key ownership with campus ops.
  6. Verification DB access is a direct MySQL read of CMS — treat as high-trust path (network allow-list, least-privilege user, no credentials in repos).
