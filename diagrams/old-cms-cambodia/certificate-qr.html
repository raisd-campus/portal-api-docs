Cambodia certificate QR + Verification

How LUCT Cambodia CMS Registry generates certificate QR codes via the external Limkokwing QR SaaS, and how public scans land on the Verification site. Evidence from Vara’s CMS pack (7 Oct 2026) and QR / Verification Drive packs (8 Oct 2026). M5 campus integration — not Lesotho M4 Applicant Demo letters.

1. Summary

Certificate QR is not generated inside Portal API or the Applicant Demo. Cambodia Registry PHP calls an external QR registry; the QR payload is a URL into the public Verification app. Vara (8 Oct): “Do check in CMS Cambodia, there's a call to the QR system to generate the QR code.”

Three systems

SystemRoleHost / path
Cambodia CMS (Registry) Builds short_code + verify URL; POSTs create API; saves PNG cambodia/registry/qrcode_gen*.php (campus SoR)
QR System (SaaS) Registers QR identity; returns base64 PNG https://qr.limkokwing.net/api/create_qrcode_api
Verification site Public scan target; shows cert validity for campus path https://verification.limkokwing.net/cambodia/{token}

2. Runtime flow

Observed from current-style qrcode_gen.php (Mar 2026). Inputs arrive as query params: StdProgramID, StudentID, ProgramCode.

Registry → QR SaaS → Verification → PNG

Short code + encrypted verify URL are sent to the create API; response PNG is downloaded.

Step checklist

  1. Build short_code = KHM-PNH_{StdProgramID} (Phnom Penh campus prefix).
  2. Encrypt StdProgramID → base64 token; build verify URL under /cambodia/.
  3. POST form fields to create API (see §3).
  4. Parse JSON; require field Qrcode (base64 PNG bytes).
  5. Decode with GD; write {StudentID}_{ProgramCode}.png; stream as download; delete temp file.

Response

  • JSON object; required field Qrcode = base64-encoded PNG.
  • Scripts also check optional message / status on failure.
  • HTTP handling notes 403 (blocked), 404, 500 in the debug-oriented generator.
  • Some variants write raw response to api_debug.log (local ops artefact — not in git).

4. Verify token & short code

Public Verification URL

https://verification.limkokwing.net/cambodia/{token}

  • {token} = base64(AES-256-CBC ciphertext of StdProgramID).
  • URL-encoded when appended (urlencode / rawurlencode depending on script).
  • QR image payload points at this URL — scanners hit Verification, not the CMS.
  • Key material lives in Registry PHP — ops secret; never republish on Pages or in git.

Short-code convention

PartValueMeaning
CountryKHMCambodia (ISO-ish campus code)
City / campusPNHPhnom Penh
Separator_
SerialStdProgramIDStudent–programme row id from CMS

Raisd should treat short-code allocation as owned by the QR SaaS + campus convention — do not invent a parallel allocator in Schema without campus agreement.

Crypto evolution (high level)

  • Current path: OpenSSL AES-256-CBC of StdProgramID alone (commented older path appended _timestamp_YYYYMMDD).
  • Legacy: qrcode_gen1.php / early helpers used mcrypt Rijndael — obsolete; not the create-API path.
  • Local-only QR: early qrcode.php built images with phpqrcode against Verification base URL — superseded by SaaS create API.

7. Raisd implications

  1. Campus integration, not Portal API core (Lesotho M4). Applicant Demo DEMO PDFs must not pretend to be this certificate QR path.
  2. Two external SoRs for QR identity: QR registry (create + short_code) and Verification (public scan). Raisd Schema should not re-allocate KHM-PNH_* without campus agreement.
  3. M5 Cambodia (and peers on the same SaaS) need an ACL/adapter that calls create API after official cert/letter issuance — TLS verify on, secrets in vault, no Cloudflare bypass hacks in production.
  4. Reference implementation: Cambodia Registry scripts are the working LUCT wiring pattern for certificate QR. Official offer/cert print remains campus-local until Raisd Live owns that desk.
  5. Other campuses may share qr.limkokwing.net with different short-code prefixes — confirm when QR System DB is inventoried.
